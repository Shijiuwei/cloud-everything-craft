# Interface languages

The app's menus, dialogs, messages and accessible names are shown in the person's language. English
is the source language; Simplified Chinese (`zh-Hans`) is the first translation.

What is translated is the **interface**. A workbook's own content is not: sheet names, table names,
function names (`SUM`, `XLOOKUP`), error values (`#N/A`), number format codes, and anything written
into a file stay as they are, so a workbook opens the same in every language, here and in Excel.
(Excel's Chinese edition keeps English function names and error values too.)

## How it works

- `src/i18n/index.js` is the runtime: `t(key, values)` returns a message as text, `tRich(key, values)`
  returns a message with markup as children for `el()`, and `formatNumber`, `formatDate`, `formatList`,
  `formatRelativeTime`, `displayName` and `compareText` format and sort for the interface language.
- Messages live in `src/locales/<language>/<namespace>.json`, one flat object per namespace, keys
  sorted. A message is asked for by `<namespace>.<key>`: `t('home.newSpreadsheet')` is the
  `newSpreadsheet` entry of `home.json`. A namespace is usually one source file (`ui/sortdialog.js` →
  `sortDialog.json`); `common.json` holds the words every dialog uses (OK, Cancel, Close…).
- Messages are [ICU MessageFormat](https://www.jkzzc.com/seo-column/httpzhuangtaimayuzhizhuzhuaquxiaolvshendujiexishizh-mvgp8o19),
  the syntax translation platforms (Crowdin, Lokalise, Phrase, Weblate…) read natively.
- English is bundled with the code. Every other language is its own chunk
  (`src/i18n/bundles/<language>.js`), loaded once by `initI18n()` in `main.js` before the first screen
  is drawn, so `t()` is synchronous. A message missing from a translation falls back to English.
- The language is chosen in this order: `?lang=` in the address, the person's choice (File ▸ Options ▸
  General ▸ Display language, kept in this browser), then the browser's languages, matched by
  language and script (`zh-CN`, `zh-SG` → `zh-Hans`; `zh-TW`, `zh-HK` are Traditional Chinese and fall
  through to the browser's next language).
- Changing the language reloads the app in place (`lib/relaunch.js`): the open spreadsheet is saved
  or kept as leaving it would, and reopens. A desktop office suite restarts to change its display
  language for the same reason: every screen is built once, in one language.
- `<html lang>` is set to the language, which is what picks the right Chinese glyphs and fonts
  (`styles/tokens.css`), the right voice in a screen reader, and the right hyphenation.

## Writing code that shows text

```js
import { t, tRich } from '../i18n/index.js';

el('button.btn', { 'aria-label': t('sortDialog.addLevel') }, t('sortDialog.addLevel'));
toast(t('sortDialog.sorted', { count: rows }));           // "{count, plural, one {Sorted # row} other {Sorted # rows}}"
el('p', {}, ...tRich('home.signIn', { link: (text) => el('a', { href }, text) })); // "<link>Sign in</link> to save"
```

- **Whole sentences.** Never build a sentence from pieces (`'Delete ' + n + ' rows'`, `` `${a} of ${b}` ``):
  word order differs between languages. Put the whole sentence in one message with arguments.
- **Plurals** use `{count, plural, one {…} other {…}}`, never `n === 1 ? '' : 's'`. `#` is the count,
  formatted for the language.
- **Numbers.** `{count}` puts a value in as given; `{count, number}` and `#` format it for the
  language (grouping separators). Use the formatted forms for quantities, the plain one for a row
  number, a year or an identifier.
- **Variants** (`{kind, select, row {…} column {…} other {…}}`) or separate keys, never a word passed in
  from English to complete a sentence.
- **Markup** goes through `tRich` with tags in the message, never `innerHTML` with a translated string.
- **Keys** are named in full where they are used: `t('sortDialog.ascending')`, or a table of full keys
  (`{ asc: 'sortDialog.ascending', desc: 'sortDialog.descending' }`). A key built at run time
  (`` t(`sortDialog.${dir}`) ``) cannot be checked or found, and the tests refuse it.
- **Identifiers are not labels.** A string that is compared, stored, used as a map key, sent to a
  command, matched with a selector or saved to a file stays English and gets a separate label for
  the screen.
- Strings for the AI model (prompts, tool descriptions, tool results) stay English. The model is
  told the interface language so its replies to the person are in it. Where the model and the person
  see the same words (a function's description), the code keeps one catalog message and hands the
  model `tSource(key)`, its English.
- **Nothing at import time.** `t()` called while a module loads runs before the language is loaded
  and stays English. A table of labels holds keys, and `t()` is called where the label is drawn.
- Dates, times and numbers in the interface (not in cells) go through `formatDate`/`formatNumber`/
  `formatRelativeTime`, or `{when, date, medium}` in a message, never `toLocaleString('en-US')`.

## Adding or changing a message

1. Add the English message to `src/locales/en/<namespace>.json` and the translation to every other
   language's file of the same name. A message is not added in English alone: the tests require
   every language to have every message.
2. `npm run i18n:format` sorts and formats the catalogs.
3. `npm run i18n:check` runs the catalog tests: every message parses; every language has the same
   keys, arguments, tags and select cases; plurals use only the forms the language has
   (`Intl.PluralRules`); every key the code asks for exists, and every key is used. For Chinese, it
   also checks the text is Chinese, with Chinese punctuation and a space between Chinese and Latin text.

Changing the meaning of an English message means changing its translations too; renaming its key
is the clearest way to make that visible in review.

## Finding text that is not translated

Open the app with `?lang=en-XA` (pseudo-localization, also offered in Display language in development).
Every catalog message is shown accented, about a third longer and between `⟦ ⟧`: plain English on screen
is hard-coded, text cut off will be cut off in a longer language, and a `⟦` without its `⟧` was truncated.

## Adding a language

1. Add it to `LANGUAGES` in `src/i18n/languages.js` with its BCP 47 tag (with a script where the
   language has more than one), its name in itself and its direction.
2. Create `src/locales/<tag>/` with a translation of every file in `src/locales/en/`.
3. Add `src/i18n/bundles/<tag>.js` (a copy of `zh-Hans.js` with the folder changed) and its loader to
   `LOADERS` in `src/i18n/index.js`.
4. Add its fonts to `styles/tokens.css` if the system font may not draw it well, and extend the
   language check in `index.html`.
5. Write a glossary like [i18n-glossary-zh-Hans.md](i18n-glossary-zh-Hans.md) first: consistent
   terms matter more than any single message.

A right-to-left language also needs the layout checked with `dir="rtl"` (the runtime sets it): the
styles use physical `left`/`right` in places.
